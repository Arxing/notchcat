# MusiCat：跨平台重寫（Rust 核心加平台層，含瀏海式與桌面浮動視窗）

寫於 2026-11-06，2026-11-18 依作者逐題確認的結果定稿。這份文件是給**要負責規劃並實作的 agent** 讀的，讀者沒有參與過先前的對話。請先讀完本文，再讀「參考文件」一節列出的文件。

## 1. 背景與意圖

專案目前叫 NotchCat，是一個只能跑在 macOS 的 Swift 程式：在有瀏海的 MacBook 上，於瀏海位置疊一個 `NSPanel`，顯示現正播放的音樂與動態歌詞。它已經實作完成（Music 模組第一版，285 個單元測試通過），但**還沒有在實機上完整驗收**。

作者想把它做成：

1. **跨平台。** 作者自己有 Windows 電腦想用，也想**開源給別人用**。Windows 沒有硬體瀏海，所以要做「假瀏海」（螢幕頂端中央的膠囊式外殼，行為仿照瀏海面板）。
2. **除了瀏海模式，還要有桌面浮動視窗模式。** 作者舉的例子是千千靜聽：一個可以拖動、放在桌面上的播放器／歌詞視窗。
3. **用 Rust 重寫整個基底。** 「功能全抽成抽象，技術細節再個別分平台實作。」
4. **新名稱 MusiCat。** 重寫版從一開始就叫 MusiCat（crate、app、文件都用這個名字）。現有 Swift 版的程式碼、目錄與 repo 名稱維持 NotchCat 不動，直到它依第 9 節被移除。

為什麼現在做：現有 Swift 程式的畫面層（AppKit／SwiftUI）無法搬到 Windows，而歌詞層、播放狀態整合這些邏輯層其實與平台無關，值得只寫一次。

## 2. 目標、非目標、反目標

**目標**

- 一個與平台無關的 Rust 核心，包含：現正播放的整合、歌詞查詢與可信度把關、快取、播放位置計算、呈現邏輯（此刻該顯示哪一行）。本地歌詞庫日後加入（第 8 節）。
- 每個與平台有關的能力（讀現正播放、送播放控制、建立並管理外殼視窗、讀螢幕幾何）都是**抽象介面**，由各平台各自實作。
- macOS 與 Windows 兩個平台；兩種呈現模式（瀏海式、桌面浮動視窗）。
- 行為與現有 Swift 版一致（見第 4 節，現有 spec 就是行為的依據）。
- 可開源給別人用：程式結構、文件、授權、風險說明要能讓陌生人看懂。

**非目標（這份設計不做）**

- Linux 支援。不刻意排除（核心不依賴特定作業系統就行），但不實作、不測試。
- 逐字（卡拉 OK 式）歌詞。精準度只需要到「此刻是哪一行」。
- 本地端自動對齊（用 AI 把純文字歌詞對上時間軸）與整個本地歌詞庫，見第 8 節。
- 公開的遠端歌詞分享服務。
- 桌面浮動視窗的換膚。
- 行動裝置。

**反目標（即使技術上成功也算失敗）**

- 顯示不準的歌詞。**寧可不顯示，也不要顯示錯的。**
- 讓 macOS 版的瀏海面板倒退：hover 閃爍、展開動畫消失、進入與離開範圍不穩定，這些問題在 Swift 版花了很多力氣才解掉（見第 5.3 節），重寫後不能再發生。
- 為了跨平台把兩個平台都做成最低共同標準，讓 macOS 版失去目前的手感。

| macOS perl 宿主 | 保留在開源版：隔離在單一 crate、預設啟用、可關閉、README 明講風險 |
| Swift 版的去留 | Rust 版在作者的 Mac 上通過**同一份**實機驗收清單（`docs/HANDOFF.md`）之後，再用一個獨立的 commit 把 Swift 版移除。在那之前 Swift 版原封不動留在 repo |
| 本地歌詞庫 | 第 8 節那一整組能力都等到 macOS 與 Windows 都跑起來之後再做（R5）。第一輪只保證資料模型與查詢流程不擋路 |
| 歌詞 | 精準度只到「此刻是哪一行」；準確優先；本地來源日後放在來源清單第一順位；本地歌詞庫日後用 git 版控；遠端分享用公開的 GitHub repo；善用使用者自己的 AI agent 產生動態歌詞（介面是本地歌詞資料夾） |
| core 的非同步與網路 | `core` 不綁定任何非同步執行環境（tokio、GPUI 的 executor 都不直接依賴），也不直接依賴 HTTP 函式庫。網路透過 `HttpClient` trait、時間與計時器透過 `Clock` trait，實際實作由 app 層注入；測試用假實作 |
| macOS 視窗繞路 | 全部集中在 `platform-macos` 裡**單一模組**，用 `objc2` 呼叫；每個繞路附註解說明原因與對應的 GPUI 版本；`shell` 與 `app` 只呼叫該模組提供的幾個函式，不碰 Objective-C。GPUI 版本**鎖定在確切版本**，升級時重跑第 5.3 節的驗收 |
| Repo 結構 | 同一個 repo，Rust 版放在頂層 `rust/` 目錄，自己是一個 Cargo workspace，不覆蓋任何 Swift 檔案。Swift 版移除之後，再決定是否把 `rust/` 的內容移到 repo 根目錄 |
| CI | GitHub Actions，macOS 與 Windows 兩個環境：`cargo build`、`cargo test`、`clippy`、`fmt` 檢查。Windows 要求編譯通過加 `core` 單元測試。視窗行為無法在 CI 驗證，靠實機驗收清單 |

**未驗證的假設（最重要的一個）：GPUI 能在 Windows 上做出假瀏海。** 作者要求先假設可行。GPUI 的 Windows 支援走 Win32 與 DirectWrite，理論上可行，但沒有人實測過。R3 的第一個任務就是驗證它；若不可行，備案是 Tauri 或一個原生 Windows 視窗（`core` 與平台層是分開的，不受影響，見第 7 節）。

### 4.1 現有行為的重點（細節以 spec 為準）

- **現正播放**：優先序清單，第一個非空的來源勝出。第一順位是系統現正播放（macOS 要透過 perl 宿主，見 6.1），備援是視窗標題（只認得 YouTube Music，沒有演出者、沒有位置、沒有封面）。
- **播放位置**：`position = max(0, elapsed + max(0, now − timestamp) × rate)`，若知道總長度就不超過總長度。位置未知時**絕不拿 0 充數**；沒有位置資訊就不捲動歌詞、不畫進度條。
- **歌詞來源**：LRCLIB 先、網易雲後。帶時間軸的結果才算「可用」並停止走訪；純文字只當保底。查詢要通過標題比對（容忍簡繁、大小寫、全半形）與長度比對（±5 秒，雙方都有長度時才比）。
- **可信度把關**：帶時間軸的結果至少 2 行；已知曲長（大於 0）時最後一行不得超過曲長加 5 秒；不通過視同該來源沒有結果。
- **快取**：成功結果永久；所有來源都乾淨回報「沒有」時快取 24 小時；有來源失敗（網路錯誤、逾時、非 2xx）時只快取 120 秒；每個來源 5 秒逾時，逾時不得拖住整個走訪；同一首歌的併發查詢共用同一次查詢；被取消的查詢不得被快取成「查無」。
- **提供者要區分「失敗」與「乾淨地沒有」**：失敗要拋錯，不是回傳空。
- **標題清理**：沒有演出者就不查歌詞；YouTube 影片標題形如「頻道名 - 曲名 ft. 他人」要先拆；`feat.`／`ft.`、`Remastered` 等括號後綴（含全形括號）要去掉，但 `(Liverpool Mix)` 這種不能誤刪。
- **畫面內容**：Preview＝左翼封面、右翼動態音柱、瀏海下方可折疊的歌詞條（沒有同步歌詞時顯示曲名）；Expanded＝封面、曲名、演出者、進度條（需要總長度與位置）、上一首／播放暫停／下一首、歌詞（同步且位置已知時跟著捲動並標示當前行，否則靜態全文）、歌詞條折疊開關；沒有曲目時一行「目前沒有播放」。
- **純文字歌詞**一律只在 Expanded 以靜態全文顯示，歌詞條改顯示曲名。

## 5. 架構

### 5.1 分層與 crate 切分

```
rust/
  Cargo.toml             # workspace
  core/                  # 與平台無關：所有邏輯，不得依賴任何作業系統 API
  platform-macos/        # now-playing（perl 宿主＋C 動態庫，獨立 crate 或獨立模組，可關閉）、
                         # 播放控制、視窗標題備援、螢幕幾何、NSPanel 視窗繞路（單一模組）
  platform-windows/      # now-playing（SMTC）、播放控制、螢幕幾何、假瀏海視窗行為
  shell/                 # GPUI 畫的外殼與內容（瀏海式、桌面浮動視窗），只透過抽象介面與平台層溝通
  app/                   # 組裝：選平台實作、注入 HttpClient 與 Clock、系統匣／選單列、TOML 設定、啟動
```

**硬規則：`core` 不得有 `cfg(target_os)`，也不得依賴任何平台 crate、非同步執行環境或 HTTP 函式庫。** 平台差異只存在於平台 crate 與 `app`。能用編譯期檢查擋住這件事的話最好（例如 CI 以只含 `core` 的方式單獨編譯）。crate 的實際命名與是否再細分，由 builder 決定，使用 `musicat-` 前綴。

### 5.2 要抽象化的介面（概念；簽章留給 builder）

| 介面 | 職責 | 現有 Swift 對應 |
|---|---|---|
| `NowPlayingSource` | 發布「目前播放的曲目快照」串流（可為空） | `NowPlayingSource` |
| `PlaybackControl` | 上一首／播放暫停／下一首；可能不可用 | `MediaRemoteControlling` |
| `LyricsProvider` | 查歌詞：成功／乾淨地沒有／失敗三種結果 | `LyricsProvider` |
| `HttpClient` | 發送 HTTP 請求（由 `app` 注入） | 無（Swift 直接用 URLSession） |
| `Clock`／`Scheduler` | 可注入的時間與排程，讓逾時、退避、輪詢都能確定性測試 | 注入的 `now`／`schedule` 閉包 |
| `ShellPlatform` | 建立並管理外殼視窗所需的平台能力：螢幕幾何、視窗類型設定（不搶焦點、跨空間、層級）、全螢幕偵測 | `NotchDetector` 與 `NotchPanel` 的平台部分 |
| `LyricsStore`（日後） | 本地歌詞庫的讀寫、列舉、監看資料夾 | 無 |

資料型別（概念，沿用 Swift 版）：`TrackSnapshot`（曲名、演出者、專輯、總長度、是否播放中、位置錨點、封面參照、來源識別）、`PositionAnchor`（elapsed、timestamp、rate）、`ArtworkRef`（識別碼加可能缺席的位元組）、`TrackIdentity`（查歌詞用的正規化曲目識別）、`Lyrics`（同步＝行的陣列，或純文字）。

**模組概念保留**：殼層只透過模組介面與內容溝通；模組提供圖示、Preview 內容、Expanded 內容、是否 active、要求的 Preview 額外高度。Music 是第一個也是目前唯一的模組。兩種呈現模式（瀏海式、桌面浮動視窗）都是「外殼」，同一份模組內容放進不同外殼。

### 5.3 外殼從 Swift 版繼承的硬性設計（數值照抄）

這些是在 macOS 實機上反覆除錯才得到的，**換了語言也必須保留**：

- **固定大小的容器視窗。** 視窗的外框在整個生命週期內不變（尺寸等於所有狀態下最大的繪製範圍），只有視窗內「畫出來的內容」做動畫。不要在動畫中改變視窗外框，否則 hover 判定範圍會跟著抖動，造成開關閃爍。
- **手動管理 hover 範圍。** 進入範圍：只有目前畫出的 Preview 外型（精準，避免滑鼠還沒碰到就展開）；一旦展開，立即把範圍放大到整個固定容器（避免輕微抖動就判定離開）。
- **離開時延遲 150 毫秒才收合**，期間若重新進入就取消。
- **兩個狀態：Preview 與 Expanded。** 寬度相同＝（瀏海寬度＋160pt），只有高度改變。Preview 高度＝瀏海高度（加上模組要求的額外高度，上限 56pt；原為 28pt，2026-11-25 為了三行歌詞條放寬）；Expanded 高度 180pt。頂端兩角是直角，下方圓角 Preview 為 10pt、Expanded 為 24pt。動畫 0.28 秒 ease-in-out。
- **Preview 內容區的左右「翼」寬度＝（寬度－瀏海寬度）÷2**；macOS 瀏海本體那一段是硬體挖洞，畫在上面的東西看不到，所以重要內容不得畫在中央。歌詞條畫在瀏海正下方（額外高度 24pt，半透明黑底，不透明度 0.6，這兩個是憑印象給的值，要實機調整）。
- **每次新的 hover 展開，模組切換列的選取都重設成目前 active 的模組。**
- **視窗必須是不搶焦點、跨桌面空間可見、不出現在 Dock 或工作列的類型，且層級高於選單列。**
- **全螢幕偵測：前景是全螢幕應用程式時面板隱藏，離開後再出現（兩個平台一致，無設定開關）。** Swift 版沒有這個行為的對照（macOS 上瀏海屬於系統層，全螢幕空間裡仍會顯示），所以 macOS 上的實作方式與是否可行由 builder 查證後回報：若 macOS 的跨空間視窗在全螢幕空間內自然被系統隱藏，就以實測結果為準，不要硬加偵測。

## 6. 平台層

### 6.1 macOS

- **現正播放**：macOS 15.4 起，系統現正播放的讀取對第三方簽章的程式一律回傳空資料。實測可行的做法是：一個很小的 C 動態庫呼叫私有的 `MRMediaRemoteGetNowPlayingInfo`，由 Apple 簽章的 `/usr/bin/perl` 以 `DynaLoader` 載入並執行，在 perl 行程內輸出一行一個 JSON 的串流給主程式。現有的 C 原始碼與線上格式在 `Sources/NotchCatMediaRemoteHelper/helper.c` 與 `HelperMessageParser.swift` 的註解與測試裡；Rust 版可以**直接重用同一個 C 動態庫與同一個 JSON 線上格式**，主程式端用 Rust 重寫行程監管（啟動、退避重啟、睡眠喚醒重啟、放棄後定期重試、stdin 關閉即終止）。
- **播放控制**：`MRMediaRemoteSendCommand` 不受上述限制，主程式自己呼叫即可（指令碼：播放 0、暫停 1、切換 2、下一首 4、上一首 5）。
- **視窗標題備援**：`CGWindowListCopyWindowInfo`。可能需要「螢幕錄製」權限（未確認），只認得 YouTube Music，沒有演出者所以不會顯示歌詞。
- **外殼視窗**：GPUI 預設建出來的視窗不是我們要的面板類型，需要一組繞路（見第 7.3 節），全部放在 `platform-macos` 的單一模組。
- **已知風險**：這是借 Apple 簽章宿主的空隙，不是正式介面，系統更新可能關掉；`/usr/bin/perl` 日後可能被移除。這個做法只適合自用與側載式散布，不適合上架。開源版必須在 README 與程式註解中明講，並且**隔離在單一 crate 或模組、預設啟用、可以在選單與 TOML 中關掉**。

### 6.2 Windows

以下是我所知的方向，**builder 必須先查證再用**，並且因為作者暫時無法實測，所有 Windows 程式碼要明確標示「未在實機驗證」：

- **現正播放與播放控制**：Windows 有官方的系統媒體傳輸控制（SMTC），WinRT 類別 `GlobalSystemMediaTransportControlsSessionManager`，可取得目前 session 的曲名、演出者、專輯、時間軸（位置、總長度、最後更新時間）、播放狀態、封面縮圖，並可送出播放／暫停／上一首／下一首。Rust 端用 `windows` crate 呼叫。瀏覽器（Chrome、Edge）與多數播放器都會註冊 SMTC。
- **位置語意**：與 macOS 同樣是「在某個時間點的位置快照」，要用同一套 `PositionAnchor` 公式推算。實作時請確認 Windows 回傳的時間軸欄位語意（尤其是播放中位置是否會自行前進、最後更新時間的基準），並以文件為準，等作者實測時再校正。
- **封面**：Windows 給的是串流縮圖，大小與格式不固定；與 macOS 一樣要以識別碼快取、置中裁切成方形顯示、可能缺席。
- **多個 session**：同時有多個播放器時，用系統回報的「目前 session」；日後可加使用者設定。
- **假瀏海外殼**：預設尺寸與位置見第 3 節。視窗要求：無邊框、透明、置頂、不進工作列、不搶焦點（類似 `WS_EX_TOOLWINDOW`／`WS_EX_NOACTIVATE`）、多螢幕與 DPI 縮放要正確（放主螢幕）；hover 判定依第 5.3 節規則；前景是全螢幕應用程式時隱藏。

### 6.3 平台無關的資料來源

歌詞提供者（LRCLIB、網易雲）是純 HTTP，放在 `core`，透過 `HttpClient` trait 發送請求。User-Agent 只寫專案名稱（MusiCat），不得帶使用者資料。

## 7. 呈現模式與畫面技術

### 7.1 兩種呈現模式

1. **瀏海式**（macOS 貼在真瀏海上；Windows 是螢幕頂端中央的假瀏海）：第 5.3 節的兩態殼層。
2. **桌面浮動視窗**（千千靜聽式）：一個可拖動的獨立視窗，顯示封面、曲名、演出者、進度條、控制鈕與歌詞（同步歌詞跟著捲動並標示當前行，純文字靜態顯示）。v1 範圍見第 3 節（無換膚；一般與歌詞專用兩種大小；拖動、記住位置、置頂切換、透明度；與瀏海模式互斥）。

兩種模式共用同一份模組內容與同一份呈現邏輯（「此刻顯示哪一行」「進度比例」「欄位缺席時怎麼辦」都在 `core`），外殼只負責擺放與視窗行為。

### 7.2 畫面技術：已決定用 GPUI

**決定：GPUI。** 在 2026-11 對 Tauri v2 與 GPUI 各做了一個拋棄式 macOS spike（同一份驗收項目），兩者都做出了瀏海 Preview 外殼。作者選 GPUI，理由是它不帶 web 技術棧、單一語言、兩平台共用同一套畫面程式碼。

spike 的實測結果（macOS 15.7、Apple Silicon、有瀏海的內建螢幕）：

| 項目 | GPUI | Tauri v2（備案，未選） |
|---|---|---|
| 視窗層級與位置 | 層級 25（選單列是 24）；bounds X=583 Y=0 345×180 | 同樣通過 |
| hover 不閃爍（以事件日誌驗證） | 通過 | 通過 |
| 展開／收合動畫 | 約 285 毫秒，通過 | 通過 |
| 閒置 CPU／每 250 毫秒重繪 CPU | 1.4%／3.4% | 0.35%／2.79%（記憶體約 137 MB，含 WebKit） |
| 中文字渲染 | 正常 | 正常 |
| 點擊穿透、跨空間與全螢幕空間、點擊不搶焦點 | **未驗證**（自動化做不到，需要人工確認） | **未驗證** |
| 打包產物的透明度 | 以 release 執行檔驗證通過 | 打包成 .app 後驗證通過（已知 issue #13415 未重現） |

GPUI 相對 Tauri 的主要代價是它**還沒有 1.0**（spike 時用 crates.io 上的 `gpui` 0.2.2；UI 元件庫可選用 Longbridge 的 `gpui-component`，由 builder 決定用不用，外殼本身直接用 GPUI 畫），內部 API 與私有類別會變動。所以：

- **GPUI 版本鎖定在確切版本**（Cargo.toml 用 `=` 固定，必要時固定到 git revision），升級是一個獨立的任務，升級後要重跑第 5.3 節的外殼驗收與實機驗收清單。
- spike 評估的信心約 65%，主要風險就是上面那些繞路是否在下一版仍然成立。

**備案**（只在 GPUI 在某個平台做不到時使用，並回報作者）：Tauri v2（macOS 需要社群的 `tauri-nspanel` 外掛，或約一百行的 `objc2` 自寫），或該平台的原生視窗。因為 `core`、平台層與外殼是分開的，換外殼不影響前兩者。

GPUI spike 的程式碼在 `spikes/gpui-notch/`（拋棄式，只是參考，不是產品程式碼；證據日誌與截圖在 `spikes/gpui-notch/evidence/`）。Tauri spike 已刪除，它的實測數字保留在上面的表格裡。重要的發現已寫在第 7.3 節。

### 7.3 GPUI 在 macOS 上需要的繞路（spike 發現）

以下全部集中在 `platform-macos` 的單一視窗模組；每一項都要有註解說明「為什麼需要」與「對應的 GPUI 版本」：

1. GPUI 建立視窗時的選項無法直接得到「無邊框、不搶焦點」的面板，需要在**視窗建立之後**再切成無邊框。
2. 為了讓面板不搶焦點、點擊不啟動 App，spike 在執行時修補了 GPUI 使用的私有面板類別的「是否可成為 key window」方法（會改變焦點行為的那個）。這是最脆弱的一項。
3. GPUI 在啟動時會把 App 顯示在 Dock 上，需要在啟動時覆蓋成不顯示 Dock 圖示（accessory 啟動模式）。
4. spike 機器沒有安裝 Metal Toolchain，編譯 shader 失敗，所以 spike 使用 GPUI 的 `runtime_shaders` 功能（在執行時編譯 shader）。開發者若裝了 Metal Toolchain 可以不用；開源版的建置說明要寫清楚這件事，並測試兩種方式。

視窗層級（高於選單列）、跨所有空間、固定大小容器與手動 hover 範圍，GPUI 本身足以做到，不需要繞路。

### 7.4 Windows 的 GPUI 驗證（R3 的第一個任務）

作者暫時無法在 Windows 實測，所以 Windows 外殼在 R3 之前沒有任何驗證。R3 開始時，**第一件事**是在 Windows 上確認以下項目（若作者此時仍無法實測，在 R3 結束時把它列為「待驗證」清單交給作者）：透明置頂無邊框、不進工作列、不搶焦點、多螢幕與 DPI 正確、hover 不閃爍、前景全螢幕時隱藏。若確認 GPUI 在 Windows 做不到其中任何一項，採用第 7.2 節的備案並回報作者。

## 8. 歌詞層的後續能力（R5，兩個平台都跑起來之後）

以下是作者已經表達的方向，**第一輪只留好介面，不實作**：

- **本地來源放在清單第一順位**：查歌詞時先看本地歌詞庫，有就直接用。
- **編輯並覆蓋**：使用者可以編輯第三方命中的歌詞（文字與時間軸），存下來即成為本地來源的一筆，之後永遠優先。
- **時間軸微調**：每首歌可調 ±0.5 秒的整體偏移並永久記住（歌詞對、時間軸整體偏掉是最常見的錯誤）。
- **「這份不對」**：列入該首歌在該來源的黑名單，改查下一個來源或不顯示。
- **儲存格式**：資料夾裡的 `.lrc` 檔加一個小型中繼資料檔（人可以直接開、改，任何工具都能寫），位置在各平台的標準應用程式資料目錄。
- **AI agent 介面**：App 把「播放過但沒有可信同步歌詞的歌」列成待辦清單檔；使用者的任何 agent 讀清單、產生 `.lrc` 檔放進資料夾；App 監看資料夾，檔案一出現就立刻生效。App 本身不內建任何模型，也不碰音訊（音檔從哪來、是否合法由使用者負責）。
- **版控與遠端**：本地歌詞庫可以是一個 git repo；遠端分享用公開的 GitHub repo，本地庫可選擇推送／拉取。
- **歌詞著作權**：公開分享歌詞有著作權風險（LRCLIB 這類社群庫本身就在灰色地帶），自用與私人庫沒問題，公開遠端庫上線前要重新評估，並在 README 說明。

第一輪重寫要確保 `LyricsProvider` 清單可以在最前面插入一個本地來源而不改其他程式碼，且快取鍵、黑名單、偏移量的資料模型沒有擋住這些能力。

## 9. 分階段與遷移

- **R0 決定關卡：已完成（macOS）。** GPUI 對 Tauri 的 spike 與選擇見第 7.2 節。尚未完成的部分：spike 未能自動驗證的三項（點擊穿透、跨空間與全螢幕空間、點擊不搶焦點）在 R2 的外殼任務中第一時間驗證；Windows 的 GPUI 驗證排在 R3 開頭（第 7.4 節）。
- **R1 核心。** `core` crate：型別、播放位置、LRC 解析、標題正規化、歌詞走訪與快取與可信度把關、呈現邏輯，含逐一移植的測試。兩個歌詞提供者（LRCLIB、網易雲）、`HttpClient` 與 `Clock` 介面（含測試用假實作）。同時建立 workspace、GitHub Actions（macOS 與 Windows：build、test、clippy、fmt）、授權檔（MIT 與 Apache-2.0）、README 骨架。`platform-windows` 在此階段只需要一個能編譯的骨架。
- **R2 macOS 平台層與瀏海外殼，達到與 Swift 版相同的行為。** perl 宿主、播放控制、視窗標題備援、Preview 與 Expanded 外殼、選單列選單與 TOML 設定，並通過 `docs/HANDOFF.md` 的實機驗收清單。這是第一個里程碑：**macOS 上的 Rust 版取代 Swift 版**。通過之後，用一個獨立的 commit 移除 Swift 版（由作者在實機驗收後下令，builder 不得自行刪除）。
- **R3 Windows。** 先做第 7.4 節的驗證，再做 SMTC 平台層、假瀏海外殼、系統匣選單。結束時附一份 Windows 實機驗收清單。
- **R4 桌面浮動視窗模式**（兩個平台，v1 範圍見第 3 節）。
- **R5 歌詞庫的後續能力**（第 8 節），可再拆成多個小階段。

開源的準備（授權檔、README、貢獻說明、CI）從 R1 就開始，不要留到最後。

## 10. 測試策略

- 核心邏輯單元測試：從 Swift 版測試逐案移植，案例與期望值照抄；時間、排程、HTTP 全部可注入，測試不得依賴真實網路、真實行程或真實播放器。
- 平台層：能用假實作測的（行程監管的退避與重啟、輸出解析、事件轉成快照）一律用假實作測；碰系統 API 的列為手動驗收項目。
- 外殼：hover 與動畫行為無法單元測試，靠 spike 的驗收項目與 R2／R3 的實機驗收清單。
- CI（GitHub Actions）：macOS 與 Windows 各跑 `cargo build`、`cargo test`、`clippy`、`fmt` 檢查；Windows 只要求編譯通過加 `core` 單元測試；只在有螢幕的環境跑的測試要能優雅跳過。
- 記憶體與 CPU：macOS 的 C 動態庫曾有每秒輪詢漏記憶體的問題（已修，自動釋放池），Rust 版的行程監管與長時間運行要有量測驗收。

## 11. 開源與風險

- **macOS 讀取現正播放的手法是自用等級的取巧**，隨系統更新可能失效，不適合上架。開源版要明講，並提供失效時的退路（視窗標題備援與「無播放資料」的優雅降級）。
- **隱私**：播放中的曲名與演出者（含任意 YouTube 影片與頻道標題）會被送到 lrclib.net 與 music.163.com 查歌詞。README 必須說明，並讓使用者可以關閉個別歌詞來源。
- **歌詞著作權與非官方介面（網易雲）**：自用無虞，公開發布與公開遠端歌詞庫需重新評估。
- **GPUI 尚未 1.0**（第 7.2 節）：版本鎖定，升級獨立成任務；macOS 的視窗繞路依賴它的內部實作，是最脆弱的點。
- **Windows 完全未驗證**（第 3 節）：GPUI 在 Windows 的假瀏海與 SMTC 的欄位語意都是假設，直到作者能實測。
- **重寫成本**：Swift 版已有約 3,400 行原始碼與 3,300 行測試，行為細節很多（見第 4.1 節）。以逐案移植測試的方式控制回歸風險。
- **Windows 假瀏海沒有硬體對照**：視覺設計（寬度、圓角、是否貼頂）沒有現成的對照，需要作者在實機上確認。

## 12. 仍待作者實機確認的事

這些不是設計問題，是需要作者的機器才能得到答案：

1. Swift 版的 20 項實機驗收（`scripts/run.sh` 與 `docs/HANDOFF.md`）。這份清單同時是 Rust 版 R2 的驗收清單。
2. GPUI spike 沒能自動驗證的三項：點擊穿透、跨空間與全螢幕空間、點擊不搶焦點。
3. 全螢幕時面板在 macOS 上的實際行為（第 5.3 節）。
4. 所有 Windows 項目（第 7.4 節）。

## 13. 留給 builder 的決定

- **規劃範圍**：先寫 R1 與 R2 的詳細任務拆解；R3、R4、R5 只寫到里程碑層級，等 R2 通過實機驗收後再細化。R3 的 Windows 程式碼可以在沒有實機的情況下寫與編譯，但一律標示「未驗證」。
- **封裝與散布**：R2 只要求從原始碼用 `cargo` 與一個等同 `scripts/run.sh` 的指令跑起來（與 Swift 版現況相同）。`.app` 打包、簽章、Windows 安裝程式、CI 的 release 工作都不在 R1 與 R2，等 R2 通過後另議。C 動態庫由 `build.rs` 建置，執行時放在執行檔旁邊的固定路徑讓 perl 找到。
- **非同步模型**：`core` 以 `Future`／`Stream` 加注入的 `Clock` 表達逾時、併發合併與取消，還是以事件加計時驅動的狀態機表達，由 builder 在 R1 開頭決定。這是 `core` 最核心的 API 決定，會影響每個移植測試的寫法，改起來很貴；請在 R1 的第一個任務寫成一頁短文件（或 ADR）說明選擇與理由，並用 Swift 版「併發合併」「取消不被快取成查無」「5 秒逾時不拖住走訪」這三類測試驗證它寫得出來。
- **選單列／系統匣圖示**：spike 只驗證了外殼視窗，沒有驗證 GPUI 的事件迴圈（加上 accessory 啟動與焦點修補）能否與狀態列圖示共存。R2 要把它當成一個小 spike：先確認 GPUI 是否有支援，沒有就用獨立的 crate（例如 `tray-icon`）或直接用 `objc2`，並把它納入「`platform-macos` 單一模組」的原則。Windows 的系統匣同理，R3 處理。
- **驗收清單的名稱對應**：`docs/HANDOFF.md` 的 20 項清單裡凡是寫死 Swift 行程名稱或指令的項目（例如 `pkill -f NotchCatMediaRemoteHelper`、`scripts/run.sh`），Rust 版沿用同一個 C 動態庫，builder 把清單複製一份改成 Rust 版的對應名稱與指令，項目內容與判定標準不變。
- crate 的實際切分與命名（使用 `musicat-` 前綴）、錯誤型別設計、TOML 的欄位名稱與位置細節、日誌方式、是否採用 `gpui-component`。
- 各平台實作的內部結構，只要符合第 5.2 節的抽象與第 5.3 節的外殼硬性規則。
- 測試工具與 CI 的細節。
- 不要為了方便而放大範圍：浮動視窗換膚、本地歌詞庫、設定視窗都不在第一輪。
